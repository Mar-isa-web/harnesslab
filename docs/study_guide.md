# HarnessLab 通读导读：为什么链条问答集

> 用法：按下面的顺序读代码，每读完一个模块先自己回答追问，再对照答案要点。
> 全部能脱口而出 = 面试防穿防达成。标注 ⭐ 的是高频追问。

## 第 0 节：这个项目到底是什么（先读这个）

**一句话：HarnessLab 是一台自己造的迷你 "ZCode"——一个让大模型能动手干活的运行时（Harness）。**

大模型本身是个关在盒子里的文字机器，没有手和眼，只会"收到文字、回文字"。
当 AI 助手"读文件、跑命令"时，动手的从来不是模型，而是它外面的 Harness：

```
你的任务 ──► Harness 打包[问题+工具说明书]发给模型
         ◄── 模型回话："我想调用 read_file(notes.txt)"   ← 模型只动嘴
      Harness 真的去读文件，把内容塞回对话
         ◄── 模型："我想写 result.txt，内容是 7"
      Harness 真的去写
         ◄── 模型："完成"
      Harness 把每一步记进 SQLite（遥测四表）
```

所以：**Agent = 模型（大脑）+ Harness（手和眼）**。ZCode = 大模型 + 复杂 Harness；
HarnessLab = 大模型 + 我们自己写的极简 Harness，主循环同构。

这个项目存在的三个理由：
1. **看穿魔术**——造过一遍后，AI 工具不再是黑盒：为什么能读文件、为什么会
   "失忆"（上下文被裁）、为什么会卡住重试（限流），全部有了体感；
2. **用数据回答 Agent 问题**——哪个模型好、哪种重试策略好，跑实验就知道。
   本项目不只是 Agent，更是"测量 Agent 的仪器"（0%→100% 实验即第一批读数）；
3. **求职硬通货**——Agent 岗面试考的就是这个循环，别人背概念，我们有代码和数据。

类比：综测小助手 = 会开车；HarnessLab = 亲手造过一台发动机。

自测：读文件的是模型还是 Harness？（答：Harness。模型只是"点菜"，Harness"做菜"。）

## 1. agent.py 主循环（最重要，从这里开始）

先看 `run()`：任务进来 → 落库开轮次 → 循环调模型 → 有 tool_calls 就过权限门执行并回填 →
没有就收最终回答 → 落库聚合。对照 docs/architecture.md §5 的时序图读。

- ⭐ **为什么重试逻辑放在 Agent 层而不是 Provider 层？**
  重试是"策略"，策略要可替换、可观测。放在 Agent 层：每次尝试（含失败）单独落
  model_usage 一行、共享 logical_request_id；换策略不用动 Provider。埋在 Provider
  里这些就测不到了。
- ⭐ **为什么权限拒绝不中断循环，而是把 denied 回填给模型？**
  真实 Harness 的行为：模型收到 permission denied 后有机会换路径（改用只读工具、
  或直接回答）。中断是 bug，回填才是可观测的行为实验。denied 也落库（status=denied）。
- **为什么 context_exceeded 标记记在 stats 里而不是外层 except？**
  真实踩过的坑：重试成功时异常被吞，外层 except 看不到，标记丢失。观测的是
  "发生过的故障"，不是"最终的结局"。
- **为什么每次工具结果要截断到 8000 字符？**
  单次工具结果不能撑爆上下文——这是真实 Harness 的铁律，截断点本身是可调参数。

## 2. telemetry.py 遥测层

- ⭐ **为什么表结构照抄 ZCode CLI？**
  三个理由：① reflect 分析脚本零成本复用；② 借鉴生产级观测维度（重试/取消/
  上下文超限/TTFT），比自己发明少走弯路；③ 能拿同样 SQL 对比自己的 mini harness
  和真实产品的行为差异。
- **为什么 model_usage 每次尝试一行而不是每请求一行？**
  重试的每次尝试都可能失败，失败数据是故障分析的核心素材。attempt_index +
  logical_request_id 让"一次逻辑请求的 N 次尝试"既分开记又能聚合。
- **为什么时间戳用毫秒整数？**
  对齐 ZCode；且跨时区无歧义，算耗时就做减法。

## 3. provider.py 模型抽象

- ⭐ **为什么手写 urllib 而不用 openai SDK？**
  ① 零依赖可审计，每一行都是自己的；② 逼自己看懂线上 JSON 格式（messages、
  tools、tool_calls 的 wire format）；③ 面试能讲清协议层而不是"SDK 帮我做的"。
- **为什么 tool_calls 参数解析要做 `_raw` 兜底？**
  模型可能吐非法 JSON 参数，硬解析会崩整个任务；兜底把原文传回去让模型自己看到错。
- **为什么要有 MockProvider？**
  ① 主循环脱离 API 可被确定性测试（15+17 项测试全靠它）；② 基准回放需要
  "同样输入必走同样路径"。errors_first 参数就是重试测试的故障注入。

## 4. retry.py 重试策略

- ⭐ **为什么退避参数是 base=0.5 / factor=2 / 上限 8s？**
  Agent 的失败多为限流和网络抖动：首退避要短（别让用户干等）、指数增长（给服务
  恢复时间）、必须封顶（防长任务挂死）。这三个数是实验变量，不是拍脑袋的终点。
- **为什么 sleeper 可注入？**
  测试里传 recorder 就能断言"确实等了、序列是 [0.5, 1.0]"，不必真睡——
  时间和随机一样，都是要被测出来的东西。

## 5. context.py 上下文策略

- ⭐ **孤儿 tool 消息是什么问题？**
  窗口裁剪可能切掉 assistant(tool_calls) 而留下配对的 tool 消息，多数 API 直接
  400。SlidingWindow 在窗口边界修剪孤儿并计数 orphan_trimmed——这个计数器就是
  "踩过真实的坑"的证据。
- **为什么 keep_head 保留任务头部？**
  任务描述在最早的消息里，裁掉 = 失忆 = 答非所问。压缩的前提是记住"我是谁、
  要干什么"。
- **为什么 summarizer 做成回调注入？**
  真实摘要接模型、离线测试接假函数，主循环不关心摘要从哪来——依赖注入让
  "需要花钱的部分"和"纯逻辑部分"分离。

## 6. tools.py / permissions.py

- **为什么工具带 write 标志？**
  权限门按副作用分级：读操作低风险放行，写操作按模式审（readonly 拒/ask 问/
  yolo 放）。这是真实产品权限设计的最小完整版。
- **为什么 run_shell 的输出要带 exit_code 和 stderr 分段？**
  模型需要知道命令是否成功、错在哪，才能决定下一步。格式化的输出是对模型的
  "API 设计"。

## 7. fault.py 故障注入

- **为什么随机要固定种子？**
  "30% 失败率"必须字面成立且可复现——同一个种子跑两遍失败序列完全一致，
  实验才可信。不可复发的实验不算实验。

## 8. benchmark.py 基准

- ⭐ **为什么判分走"写文件后比对"，不解析模型回答文本？**
  回答措辞有歧义，文件内容可逐字符比。判分器的确定性是基准的地基。
- **为什么有 --self-test？**
  测测试的测试：用标准答案反向验证判分器本身正确，保证任务集先于模型可信。

## 9. 实验结论的追问链（简历行的防御工事）

以核心结论"注入限流下立即重试 0% vs 指数退避 100%"为例，连环追问的答案链：

1. 为什么 0%？——注入连续 2 次 429，immediate 只有 2 次尝试（1 重试），全灭。
2. 为什么 backoff 能活？——max_retries=3 给了 4 次尝试，第 3 次恢复；等待 0.5+1.0s。
3. 干净条件下有差异吗？——没有（9/10 vs 10/10，重试根本不触发）。
   **说明鲁棒性收益只能在故障条件下测量，故障注入是必选项。**
4. 样本量够吗？——10 任务/轮，且发现 ~10% 的模型行为波动，
   所以正式结论应多轮取均值（已列为后续实验）。
5. 恢复代价是什么？——均值 12.6s/任务 vs 干净 4.3s，其中退避等待 ~1.5s，
   其余是重跑的模型请求。可靠性买的是延迟，这笔账要算给面试官听。
