# UsageLab 架构设计（含每个决策的"为什么"）

## 1. 总体形态：ETL 三段式，无守护进程

```
db.sqlite ──load(只读)──► 各指标模块(SQL/Python 计算) ──► report(md/html/快照)
```

**为什么不做常驻服务/定时任务？** 数据源是个人本地库，受众是自己；
按需一条命令比守护进程少了常驻内存、端口、崩溃恢复三类问题。
"每周跑一次"的节律由人的复盘习惯驱动（训练计划本身是每周验收），
机器自动化的收益小于其复杂度成本。等需要趋势告警时再加 cron，YAGNI。

## 2. 分层与依赖方向

```
load（最底层：连接/时间窗/周分桶/格式化）
 ├── metrics   ├── models    ├── sessions  ├── signals   （指标层，只依赖 load）
 └── weekly（依赖 load+metrics+signals）
report / report_html（渲染层，依赖全部指标层）
cli（入口，只调渲染层）
```

**为什么 week_key 放在 load 而不是 weekly？** signals 要按周聚合信号，
weekly 要按周聚合轮次，二者互相 import 会成环。时间分桶是通用工具，
下沉到最底层，谁都可以依赖（踩过的坑：初版 signals↔weekly 循环导入）。

## 3. 关键设计决策

### 3.1 只读连接（mode=ro URI）
db.sqlite 是用户全部 AI 协作历史的**唯一载体**，观测工具写坏它 = 不可逆事故。
SQLite 的只读 URI 在驱动层拒绝一切写操作，比"约定不写"可靠。
测试还专门断言了"只读连接执行 CREATE 必须失败"——把戒律变成机器验证。

### 3.2 合成库测试（build_fixture.py）
真库数据天天变，只能断言"跑通了"；合成库每个数字已知，可以断言
"P90 必须等于 40s"。schema 与真库同构（列裁剪到被查询的部分），
fixture 常量（W1/W2、耗时数组、信号文本）同时服务于数据和断言，
两边不会漂。**指标代码的 bug 在这里被抓**——本项目开发中真实抓到过
dict 解包残留导致的崩溃和周分桶把取消轮混入耗时分布两处。

### 3.3 完成轮与取消轮分开统计
耗时分布只算 `completed_at IS NOT NULL` 的轮；取消轮单独算 cancel_wait。
**为什么**：两类等待语义不同——完成轮是"AI 干完的时间"，取消轮是
"用户忍到极限的时间"。混进同一个 P90 会让数字既不能回答"AI 多快"
也不能回答"用户多不耐烦"。取消率、取消前等待中位才是体验的真相。

### 3.4 会话卫生 = 属于「曾超 1M 的会话」的全部轮次占比
**为什么不是"单轮输入>1M 的轮次占比"**：训练目标是"新任务开新会话"，
坏的是"在一个膨胀会话里继续工作"这个行为。会话一旦膨胀，后续每一轮
都付出 10 倍耗时（见上下文×耗时读数），所以该会话全部轮次都计入。
含取消轮：被取消的往往是膨胀会话里最痛的轮，漏掉会低估问题。

### 3.5 周界用本地时区周一，分桶在 Python 侧
SQL 里按 UTC 天切周，UTC+8 的周一凌晨请求会落进上一周。训练验收
对周界敏感（达标/不达标二值），宁可多拉 raw 行在 Python 分桶。

### 3.6 分位数口径 = int(n·p) 最近邻
与历史复盘脚本（analyze_step1.py）保持同一口径，新旧读数可直接对比。
教材上有更精细的插值定义，但**口径的连续性比单点的精确性重要**——
换口径等于把历史基线作废。

### 3.7 信号词典带权重，消息级去重不做
放弃/否定 ×3、纠错/重做 ×2、抱怨/追问 ×1：重度信号对"协作质量"的
信息量远大于轻度抱怨。同一消息命中多类算多次（"图片不对，重新生成"
= 视觉+纠错+重做）——**多类命中本身就是信号强度的体现**。词典硬编码
在 signals.py（M3 再外置）：词典变更应该是显式的代码决策，不该被随手改。

### 3.8 采集与渲染分离，safe() 包裹每段
`build_report()` 对每个指标段 try/except，失败段落渲染成"跳过"而不是
炸整份报告。不同版本 ZCode schema 有列差异，**观测系统的可用性
优先于单个指标的完备性**。渲染层用 `_ok()` 统一判定段落可用。

### 3.9 HTML 自包含（CSS 内联 + 图表 base64）
报告的使用场景是"发给别人看/存档/打印"——单文件不依赖目录里的图片。
matplotlib 缺失时自动降级纯表格：核心指标不因可选依赖缺席而丢失。

### 3.10 指标快照（history/*.json）
每次运行存核心指标快照。周对比不需要"记得上周数字"，直接 diff 快照。
数据库会被 ZCode 压缩/清理，快照是不可变的观测历史——
**观测系统的输出本身也要可观测**（时间序列化）。
